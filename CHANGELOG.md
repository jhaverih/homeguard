# Changelog

All notable changes to the Attenteve platform (api, admin, vendor, mobile, infrastructure) are documented in this file.

## How this file works

This project deploys continuously (`git push origin staging` triggers an automatic build+deploy via a self-hosted GitHub Actions runner — see `.github/workflows/staging.yml`), not via discrete tagged releases. So instead of strict [Semantic Versioning](https://semver.org) release sections, entries are grouped **by date**, newest first. That said:

- **Every commit that changes deployed behavior gets a dated entry here, added in the *same commit* as the code change** — not as a follow-up, not batched later. If you're committing a fix or feature, update this file first.
- Categorize each entry as **Added** / **Changed** / **Fixed** / **Removed**, and tag which app(s) it touches: `api`, `admin`, `vendor`, `mobile`, `infra`.
- One or two sentences per entry: what changed and why (the "why" matters more than the "what" — the diff already shows what). Link to a memory file or plan doc instead of re-explaining background that's already written down elsewhere.
- Bump the version in the root `package.json` on any entry meaningful enough that "what version are we on" is a question someone might ask — a new customer/vendor-facing feature or a fix for a production incident. Routine internal refactors don't need a bump. Use semver loosely: patch for fixes, minor for additive features, major only for a genuine breaking change to a public API contract.
- This file starts at the point version-conscious changelog discipline began (2026-07-19, version bumped `0.0.1` → `0.2.0` to reflect that substantial platform work already shipped before this practice existed — see "Earlier history" below, reconstructed from project memory rather than tracked in real time). Going forward, don't let it drift out of date the way the pre-2026-07-19 history did.

## 2026-07-31 (4)

### Fixed
- **mobile**: The previous entry's immediate silent retry on a network error still failed in the exact scenario it was meant to fix — confirmed live: nginx logged a `499` and cloudflared logged "Incoming request ended abruptly: context canceled," meaning the request *did* reach the server but the client itself cancelled the connection (consistent with the OS suspending the app's networking on backgrounding). Retrying immediately in that same moment doesn't reliably help, since networking may still be suspended right then. Now: a network error while the app is still in the foreground gets one immediate retry (a genuine blip); a network error while backgrounded holds the message and retries once the app is actually back in the foreground (`AppState` listener), instead of guessing blind. Either way the customer just keeps seeing "eveAi is thinking…" — no error shown unless a foreground attempt genuinely fails.

## 2026-07-31 (3)

### Fixed
- **mobile**: eveAi replies (which can take anywhere from a few seconds to over a minute) sometimes failed with "can't connect to the server" for no server-side reason — confirmed live: the request never even reached the server. Root cause is a well-known mobile OS behavior, not a bug in our stack: locking the phone or backgrounding the app while a long request is in flight can get its connection killed by iOS/Android before a reply arrives. The chat screen now silently retries once on a network error (still shows "eveAi is thinking…" throughout) before showing anything to the customer, and the eventual error message — if the retry also fails — now explains what's actually happening instead of the old, inaccurate "make sure you're on your home WiFi" (the app talks to a public Cloudflare-tunneled endpoint, not a LAN-only one, so WiFi was never actually the issue). Fixed the same inaccurate copy on the login screen too.

## 2026-07-31 (2)

### Fixed
- **api**: eveAi recommended "House Cleaning" after answering an unrelated wasp-removal question — reported live. `matchCatalogFromText`'s deterministic catalog-recommendation fallback matches any distinctive word from a catalog item's name against the customer's raw message; "house" is a real word in "House Cleaning" but is also present in nearly every home-maintenance message ("wasps in my house," "my house needs..."), so it fired on almost anything. Added "house" to `CATALOG_MATCH_STOPWORDS`, same treatment already given to "home" for the identical reason — pre-existing bug, not introduced by this session's other changes, just surfaced by wider live testing.

## 2026-07-31

### Added
- **api**: eveAi now has an explicit safety policy — declines requests involving violence/harm toward a person or animal, hate speech, discrimination, or anything else outside home-maintenance scope, with a one-sentence decline-and-redirect rather than a lecture. Self-harm/suicide is handled separately and deterministically (matched before the message ever reaches the model, so this never depends on the model's judgment): a warm, brief response pointing to the 988 Suicide & Crisis Lifeline instead of a normal reply. Explicitly instructed *not* to flag ordinary home-maintenance language that overlaps with violence-adjacent words — "kill the breaker," pest "trap"/"poison," "shoot" a nail gun, cutting materials, a fireplace — since a naive keyword filter in this specific domain would false-positive on completely normal questions.

## 2026-07-30 (7)

### Fixed
- **api**: eveAi gave a completely off-topic reply to "How to fix a tile" — a garbled mix of gutter, HVAC/furnace, and caulk/door/window content, never anything about tiles. Root cause: `buildSeasonalAndCatalogContext()` unconditionally injected the full current-season + annual maintenance-tips list (16 lines) into every single turn's context regardless of what was asked — the `isHowToRequest()` gate added last round only covered the bookable-services half of that function, not the seasonal-tips half. "Tile" also isn't one of the 39 curated DIY topics, so there was no grounded content for the model to draw from — just two irrelevant reference blocks it pattern-matched fragments from instead of admitting it lacked specifics. Gated seasonal tips behind the same how-to check, added an explicit instruction telling the model not to repurpose unrelated reference material when nothing specific is available, and added a `loose_cracked_tile` DIY topic so this exact case now has real grounded guidance.

### Changed
- **infra**: Moved eveAi's Ollama host off a personal laptop (192.168.86.37) onto a dedicated always-on Windows PC on the same LAN (`EBO001`, 192.168.86.35 — AMD Ryzen 5 7520U, 15.3GB RAM), configured via a SYSTEM-level Scheduled Task so it survives reboots without requiring anyone to be logged in. The laptop wasn't a real server — it sleeps, powers off, changes networks — which explained an intermittent `Ollama pre-warm failed: connect ETIMEDOUT` already visible in deploy logs. Also upgraded the model from `llama3.2:1b` to `llama3.1:8b`, comfortably within the new host's RAM, for meaningfully better instruction-following — the 1b model's weakness was the underlying reason a small local model could pattern-match irrelevant context into a wrong answer in the first place.

### Fixed
- **mobile**: The previous entry's theory (Android's `adjustResize` and `KeyboardAvoidingView behavior="padding"` double-compensating) was wrong — reported live via screenshots showing it made things strictly worse: typed text in registration fields became invisible, and the eveAi chat input bar disappeared entirely while the keyboard was open. Most likely this app's edge-to-edge display mode (common on modern Android/Expo targets) means Android's native `adjustResize` doesn't reliably resize the content the way the previous fix assumed, leaving `behavior="padding"` as the thing actually doing the work on Android too, not just iOS. Reverted `behavior="padding"` back to unconditional on all 17 screens. Solved the two originally-reported problems instead with targeted `Keyboard.dismiss()` calls: the registration address picker already dismissed on selection (kept from the prior entry); eveAi's chat now also dismisses immediately when a message is sent, rather than only after the reply arrives — the keyboard was covering the "eveAi is thinking…" indicator for the entire wait (which can run to several minutes), not just briefly.

## 2026-07-30 (5)

### Fixed
- **mobile**: The scroll-to-reveal fix in the previous entry didn't actually resolve the reported "hidden behind keyboard" symptom, and the same class of bug was also reported on the eveAi chat screen (the "eveAi is thinking…" indicator hidden behind the keyboard while waiting for a reply). Root cause found to be systemic, not screen-specific: `AndroidManifest.xml` already sets `android:windowSoftInputMode="adjustResize"`, meaning Android itself already resizes the app's window to avoid the keyboard — but every screen in the app (18 places) also wrapped its content in `KeyboardAvoidingView behavior="padding"` unconditionally, which is the *iOS* technique for the same problem (iOS doesn't resize the window, so the app has to pad manually). Doing both at once double-compensates and produces exactly this kind of incorrect/insufficient spacing on Android. Changed `behavior="padding"` to `behavior={Platform.OS === 'ios' ? 'padding' : undefined}` across all 17 full-screen instances of the pattern (login, registration, password reset/forgot/verify, dispute filing, all three marketplace booking forms, both profile screens, home dashboard, service request, vendor active-job, and both chat screens) — Android now relies solely on the OS's own resize behavior, iOS is unchanged. Left the one remaining instance (vendor active-job's task-entry `Modal`) as-is, since Android `Modal`s render in a separate native window with different keyboard-resize semantics and it wasn't a reported/confirmed case. Also replaced the registration address-picker's scroll-to-reveal attempt with `Keyboard.dismiss()` on selection instead — simpler and no longer needed now that the root cause is fixed, but also more robust on its own (the field's job is done once an address is picked, matching how Google Maps/Uber autocomplete behaves).

## 2026-07-30 (2)

### Fixed
- **mobile**: The new "Location Not Sent" alert (below) started firing on a real device with Location Services confirmed on, so the earlier fix just made a pre-existing failure visible rather than causing one. Root cause, found by reading the `expo-location` Android module source directly: `getCurrentPositionAsync` defaults `mayShowUserSettingsDialog` to `true`, which on a phone where the separate Wi-Fi/Bluetooth-assisted "network location" setting is off (distinct from the GPS toggle) makes the call depend on the vendor tapping a system "Improve Location Accuracy?" resolution dialog before it resolves — miss that tap and it throws `LocationSettingsUnsatisfiedException`, indistinguishable to the vendor from any other failure. Now passes `mayShowUserSettingsDialog: false` to go straight to GPS instead of depending on that extra interactive dialog. Also logs the underlying error via `console.warn` on failure (not shown to the vendor) so a future occurrence is diagnosable from logcat instead of another blind investigation.

## 2026-07-30

### Fixed
- **mobile**: Found while investigating a live test where "Vendor en route" showed with no ETA and no map — the vendor's location-report retry interval was only ever created *after* the first GPS fetch succeeded, so a single transient failure (indoors, still acquiring a fix, Location Services toggled off, ...) silently disabled tracking for the rest of the job with no retry and no error shown. Confirmed live: the test job's `vendorEnRouteAt` was set (status advance succeeded) but `vendorLatitude`/`vendorLongitude`/`vendorLocationAt` were all null (location was never captured). The retry interval is now always created regardless of whether the first ping succeeds, and the vendor now sees a clear "Location Not Sent" alert if the very first attempt fails, instead of it failing silently with no way to know or recover.

## 2026-07-29 (2)

### Fixed
- **mobile**: The vendor's GPS location-reporting loop (fires every 90s while `VENDOR_EN_ROUTE`) is a plain JS interval, and Android doesn't reliably suspend it just because the app is backgrounded — it could keep polling GPS + making a network call for a while after the vendor locked their phone, draining battery for no visible benefit. Now explicitly paused via `AppState` the moment the app leaves the foreground, and resumed (with an immediate fresh ping, not a stale wait) the moment it returns, only if the job is still en route. Applied the same pause/resume to the customer's lighter ~35s auto-refresh poll (`request-detail.tsx`) for the same reason.
- **api**: eveAi was leaking its internal "Bookable services" catalog listing (every active, customer-requestable service — Blinds & Curtains, Mirrors & Artwork, Mailbox Installation, ...) into the visible reply on DIY/how-to questions, before eventually giving the real answer — reported via a "how do I fix a baseboard" example that showed the whole catalog dump first. Root cause: `buildSeasonalAndCatalogContext()` injected that full list plus a `RECOMMEND:` booking-suggestion instruction into every single turn's system prompt with no instruction telling the model not to echo it back, and — since baseboard repair isn't one of the specific DIY-topic keywords — the existing DIY-guidance detection never caught this case at all. Added a broader `isHowToRequest()` keyword detector (independent of the specific DIY-topic list) that now skips the entire bookable-services block for how-to-phrased questions — there's no reason to show it, and doing so was directly contradicting the system prompt's own "DIY guidance and booking are separate" rule. For the remaining genuinely booking-relevant questions where the catalog list is still shown, added an explicit instruction that it's private reference data never to be printed back to the customer.

### ~2026-07-09 — Fixed (vendor, mobile)
