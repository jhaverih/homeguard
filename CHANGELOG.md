# Changelog

All notable changes to the Attenteve platform (api, admin, vendor, mobile, infrastructure) are documented in this file.

## How this file works

This project deploys continuously (`git push origin staging` triggers an automatic build+deploy via a self-hosted GitHub Actions runner — see `.github/workflows/staging.yml`), not via discrete tagged releases. So instead of strict [Semantic Versioning](https://semver.org) release sections, entries are grouped **by date**, newest first. That said:

- **Every commit that changes deployed behavior gets a dated entry here, added in the *same commit* as the code change** — not as a follow-up, not batched later. If you're committing a fix or feature, update this file first.
- Categorize each entry as **Added** / **Changed** / **Fixed** / **Removed**, and tag which app(s) it touches: `api`, `admin`, `vendor`, `mobile`, `infra`.
- One or two sentences per entry: what changed and why (the "why" matters more than the "what" — the diff already shows what). Link to a memory file or plan doc instead of re-explaining background that's already written down elsewhere.
- Bump the version in the root `package.json` on any entry meaningful enough that "what version are we on" is a question someone might ask — a new customer/vendor-facing feature or a fix for a production incident. Routine internal refactors don't need a bump. Use semver loosely: patch for fixes, minor for additive features, major only for a genuine breaking change to a public API contract.
- This file starts at the point version-conscious changelog discipline began (2026-07-19, version bumped `0.0.1` → `0.2.0` to reflect that substantial platform work already shipped before this practice existed — see "Earlier history" below, reconstructed from project memory rather than tracked in real time). Going forward, don't let it drift out of date the way the pre-2026-07-19 history did.

## 2026-08-20

### Fixed
- **api**: `Home Sensors`/HVAC Analytics connectivity status was computed purely from `lastReportedAt` age vs. a fixed 2-hour window — confirmed live against a tagged HVAC drain-pan sensor that this produced false "disconnected" readings (and a repeating false `Device.Disconnected` alert every ~30-90 min, fired 5 times in one day) for a sensor Yolink's own cloud still reports as genuinely online; some sensor types (e.g. a LeakSensor sitting in normal/dry state) legitimately go 3+ hours between MQTT reports without being disconnected. New `YolinkDevice.isOnline` column captures Yolink's own connectivity flag directly (from `<deviceType>.getState`, refreshed every Monitoring-tab load) and is now authoritative over report-age staleness for both the customer-facing streaming dot and the disconnect-alert cron — the age heuristic only applies as a fallback for a device never yet checked via `getState`.

## 2026-08-17

### Added
- **mobile**: Customer app's "Alerts" tab is now "Monitoring" (5th of 7 tabs, same badge behavior), and the screen now opens with a "Home Sensors" grid (live tiles for the customer's actual linked Yolink devices: today that's one temperature sensor + two water leak detectors, nothing hardcoded/placeholder) above the existing alert feed, plus a static Home Assistant upsell teaser at the bottom. Each tile shows a green/red status dot reflecting whether that device has reported within the last 2 hours (`isStreaming`, not tied to the sensor's reading itself — a leak sensor actively detecting a leak while still reporting is green, the leak shows as its text state) and a formatted reading (°F for temperature, Dry/Leak Detected for leak sensors). The Recent Alerts list caps to roughly 3 cards tall with its own internal scroll, matching the mockup, so the Home Assistant teaser is always reachable without scrolling through every alert first.
- **api**: New `YolinkDevice` catalog table (`yolink_devices`) and `GET /yolink/devices` endpoint. Previously the Yolink integration only ever persisted alert-worthy events into the `Alert` table — routine MQTT "report" messages (which carry live temperature/leak-state data) were silently dropped, and `Home.getDeviceList`'s per-device `type` field was fetched but discarded. Now every incoming MQTT message (alert or not) upserts the matching device's `lastReportedAt`/`lastState`, and the customer's Monitoring tab additionally triggers a live REST reseed via `Home.getDeviceList` on load/pull-to-refresh so devices don't show red just because they haven't reported since deploy. The endpoint returns only `THSensor`/`LeakSensor` devices — any other Yolink device type is excluded, not just hidden.

### Changed
- **mobile**: Monitoring (formerly Alerts) is now available on every paid plan, including CarePlus — previously the tab's own upsell gate incorrectly treated CarePlus the same as the free tier and hid it. Moved to the 5th tab position, and its header now matches the dashboard mockup exactly (logo/role-switch row plus a "Dashboard" title on the dark header background at the mockup's own 22px/700 weight, replacing the plain one-line tab title — the tab bar label itself stays "Monitoring"). The Recent Alerts scroll cap was also undersized and clipped the 3rd card mid-text — increased to fit a full 2-line card.
- **api/mobile**: Every Home Sensors alert used to show as a generic "Info" badge regardless of what actually happened. Temperature/leak alerts now split into two categories: **Alert** (an actual threshold crossed — low/high temperature, flooding detected) and **Info** (device-health noise — low battery, routine status restatements, and a new "sensor disconnected" case). Previously a low-battery trip on a leak sensor was mislabeled "Water leak detected!" since the event handler never checked which alarm flag actually fired — it now branches on `data.alarm` the same way THSensor already did.
- **api**: New scheduled check (`YolinkService.checkDisconnectedSensors`, every 30 min) raises an Info alert the first time a monitored device goes quiet for over 2 hours, instead of that only being visible as a red dot on the next Monitoring-tab visit. Fires once per silence (tracked via a new `YolinkDevice.disconnectAlertedAt` column) and clears automatically as soon as the device reports again.

### Fixed
- **api**: The Alert/Info reclassification above only changed how *new* alerts are scored — existing rows created before that change still carried their old severity, so already-created alerts kept showing "Info". Added a one-time startup backfill (`YolinkService.backfillAlertSeverity`) that re-derives severity for existing THSensor/LeakSensor alerts from their already-stored raw payload, using the same resolver new alerts use. Idempotent, runs every boot, no-ops once everything matches.

## 2026-08-19

### Fixed
- **api**: A real Yolink MQTT payload (confirmed against a live test alert) has no top-level `deviceType` field at all — only `simulateAlert()`'s synthetic test payload did. Every alert from a real device was falling through to a generic "Device: ..." message (e.g. "Device: Water leak detected!" instead of "Laundry Leak Sensor: Water leak detected!") because both the `deviceType` field and the in-memory device-name cache lookup came up empty. `deviceType` is now derived from the event name itself (`"LeakSensor.Alert"` → `"LeakSensor"`, the same trick `simulateAlert()` already relied on), and the alert's device name now reads from the persisted `YolinkDevice` catalog row first — which is always fresh — instead of the in-memory name cache, which only refreshes on MQTT reconnect and can lag well behind a sensor added mid-session. A one-time startup backfill (`backfillAlertDeviceInfo`) corrects the name/type/message on already-created "Device: ..." alerts using the same resolver. Separately confirmed the reported "sensors show red/not connected" wasn't a backend bug — direct DB inspection showed `lastReportedAt` updating correctly on every alert; the screenshot was simply from before the most recent report came in.
- **api**: `refreshDeviceStates` (the REST reseed that runs on every Monitoring-tab load, meant to confirm a sensor's connectivity without waiting on it to report over MQTT) was checking `Home.getDeviceList` for `state`/`online` fields that — confirmed live against the account above — that endpoint never actually returns; it's metadata only (name/type/token). It now calls Yolink's real per-device live-state query, `<deviceType>.getState` (using each device's own token, now persisted as `YolinkDevice.yolinkToken`), which does return genuine `online`/`reportAt`/`state` data — applied identically to every monitored device type (temperature and leak sensors alike), so a sensor that's connected but simply hasn't reported over MQTT yet (e.g. a leak sensor sitting quietly in its normal/dry state) can still show green on the next tab load instead of waiting indefinitely for its next spontaneous report.

### Added
- **api/mobile/admin**: First real slice of the Attenteve HVAC Analytics platform (mockups reviewed and approved this session — see the plan doc for the full spec interpretation and rule-implementation roadmap). New device tagging system: `YolinkDevice` gained `room`/`equipmentId`/`sensorRole`/`analyticsRole` columns, keyed off the device's immutable `deviceId` (Yolink EUI) and never re-derived from its customer-editable name, plus a `YolinkNameTaggingRule` auto-tagging table seeded with the spec's exact Room/Equipment/Sensor Role/Analytics Role mappings (`ATV HVAC Drain Pan`, `ATV Washer Drain Pan`, `ATV Indoor Temperature`, `ATV HVAC Return Air`, `ATV HVAC Supply Air`) — a device gets tagged automatically the first time its Yolink name matches a rule, and stays tagged even if later renamed. New `SensorReading` table captures time-series history for analytics-tagged devices (nothing captured this before — `YolinkDevice` only ever kept the latest snapshot). New `AnalyticsFinding` entity implements the spec's event schema (severity/confidence/reason codes/recommended actions), with a static `RULE_CATALOG` covering all 21 spec rules so "not available for this customer" reporting is honest even for rules that aren't executable yet. Implemented and wired live: water/condensate detection (HVAC-WATER-001/002/003, CRITICAL, with the spec's exact copy and actions — the highest-priority rule per the spec), low/high indoor temperature (CarePlus-eligible), sensor offline/low-battery (HVAC-SENSOR-001/002). Rules needing supply/return air sensors, thermostat integration, power monitoring, or baseline history (none of which exist yet) correctly report as unavailable rather than guessing.
- **mobile**: New HVAC Analytics page (`/(customer)/hvac-analytics`, reached via an entry point inside Monitoring — no new tab bar icon) showing the health "Learning" state honestly, active findings (the water-detection CRITICAL card with `I Fixed It`/`Get Attenteve Help`/`Dismiss`), sensor coverage, and a "Request HVAC Contractor Visit" button. CarePlus customers see indoor-temp/leak findings only, with a real upgrade prompt for HVAC performance analytics instead of a stripped-down freebie view — matching the plan's tier gating (`PlanTier.BASIC` = CarePlus, `STANDARD`+ = Proactive).
- **admin**: New HVAC Analytics page (`/hvac-analytics`) — customer search (type-to-filter dropdown), a summary strip, per-role time-series charts (`recharts`) built from real `SensorReading` history, a findings timeline, a sensor coverage table, and a "Rules Not Available for This Customer" panel naming the exact missing sensor/integration/baseline gate per rule.

### Changed
- **api/mobile**: A verified card must always stay on file — a customer can have an outstanding/ongoing service that still needs to be paid through the platform even after cancelling their subscription. With only one card on file, its action is "Replace" (collects a new card via the existing Stripe PaymentSheet flow first, and only detaches the old one — now promoted default — once that succeeds; nothing changes if the sheet is cancelled). With multiple cards, a non-default card can be removed directly, but the *default* card cannot — the customer must switch default to another card first, then the now-non-default old default becomes removable. `PaymentsService.removePaymentMethod` enforces both rules as hard backend invariants (rejects removing a customer's last card, and rejects removing the default card directly) regardless of call path.

## 2026-08-12

### Fixed
- **api**: **Login was broken for every account since 2026-08-09**, not just unverified ones — `UsersService.findByEmail`'s explicit `select` array never included `isEmailVerified`, so it read as `undefined` (falsy) for every login attempt regardless of the real value, meaning the verification check added that day rejected everyone. Found while investigating a report that a definitely-verified admin account (`isEmailVerified: true` in the DB, confirmed via direct query) still couldn't log in — nginx logs showed real 403s hitting the backend that never appeared in the app's own logs, since a deliberately-thrown `ForbiddenException` isn't logged as an error by NestJS's default handling, which is why this took real digging to surface. `isEmailVerified` added to the select list; `findByEmail` has exactly one caller (`login()`), so this was fully isolated.
- **api**: Admin and vendor-technician accounts created via the team-invite flows (`AdminService.createTeamUser`, `VendorService.createTechnician`) were never marked `isEmailVerified` — neither flow has any verification UI (that only exists in the mobile registration wizard), so once login started requiring verification (2026-08-09), any account created this way could never log in at all. Both now mark the invited account verified immediately at creation — the inviting admin/company-owner is already vouching for the email.

### Added
- **api/admin/mobile**: 6 handyman/repair categories (Interior Repairs, Electrical, Plumbing, Mounting/Installations, Carpentry, Exterior/Outdoor — Inspections unaffected) switched from a fixed per-item GM% to a dynamic, graduated GM% looked up from total vendor cost (tiered service cost + material costs the vendor logs during the job), replacing materials' old flat 15% markup for these categories. Graduated like tax brackets, not a flat lookup — a flat "whole amount gets one bracket's rate" table makes price *drop* at every boundary (verified by hand: $150 → $240.00 but $151 → $223.70 under a flat lookup), so each portion of cost prices at its own bracket's rate and the results are summed; confirmed monotonic at all 4 boundaries with the actual bracket values (midpoints of $0–150→35–40%, $151–500→30–35%, $501–1,000→25–30%, $1,001–2,500→20–25%, $2,500+→15–20%). Bracket table is a backend constant (`pricing.utils.ts`), not admin-editable. Booking-time shows an estimate (tiered cost alone, no materials yet exist); materials logged mid-job stay invisible to the customer (price 0, no notification) until the job completes, at which point the real combined-total price finalizes — materials reveal at their raw logged cost, the main service line absorbs the rest (margin + Stripe fee), reusing the existing quantity-reconciliation-recalc and "Final Price Updated" notification mechanism. Admin Services Management page shows "Calculated" (read-only) instead of an editable number for these categories' GM% field, and its preview/formula-reference text is explicitly labeled as a booking-time-only estimate.

## 2026-08-06

### Fixed
- **api**: A vendor could accept (or reschedule) a service request into a date/time that had already passed — nothing validated this anywhere, client or server. Most commonly hit when a request sits `PENDING` long enough (never picked up, or released/rejected by an earlier vendor) that its `preferredDate` goes stale before a vendor finally responds.
